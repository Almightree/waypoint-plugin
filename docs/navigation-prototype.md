# Navigation-arrow prototype

`AlmightreeWaypoint` is a separate addon from `WaypointProbe`. It draws only in addon-owned frames, observes the player's active tracking type, and leaves all waypoint/super-tracking state alone. The probe remains available independently for diagnostic captures.

The display is a transparent overlay: only the arrow and text are drawn, with no panel background or border, including with EUI skinning enabled. EUI still supplies the public font and accent styling.

## Install and controls

1. Copy the repository's **AlmightreeWaypoint** folder to `<WoW>/Interface/AddOns/AlmightreeWaypoint`. Its TOC, Lua files, and `Arrow.tga` must be directly in that folder.
2. Optionally copy **WaypointProbe** alongside it. Neither addon depends on the other.
3. Install/update EllesmereUI if you want its settings page and styling. The arrow uses `OptionalDeps: EllesmereUI` and also runs without EUI. EUI's optional `/way` module does not need to be enabled.
4. Restart the client or `/reload`, confirm the addon is enabled in the addon list, and run `/atway preview`. The first-install default is enabled and locked. Preview is synthetic and not evidence of live navigation.

The TOC uses the same candidate interfaces as the probe (`120100, 120105, 16001`). This is not a tested compatibility matrix. One shared implementation is used; Forever testing is **blocked until after November 4, 2026**. No compatibility or taint-free claim is made.

| Command | Behavior |
| --- | --- |
| `/atway enable` | Enable observation and event-driven navigation |
| `/atway disable` | Hide the display, clear target data, unregister navigation events, and remove active updates; also works in combat |
| `/atway preview` | Toggle a static synthetic preview; entering preview enables the addon if disabled |
| `/atway unlock` | Show a static preview/mover; drag anywhere on the panel with the left mouse button |
| `/atway lock` | Disable dragging and resume navigation, unless explicit preview remains enabled |
| `/atway reset` | Reset only position to centered, 180 UI units above screen center |
| `/atway options` | Open the public EUI plugin page when available |

Disable explicit preview with `/atway preview` and lock with `/atway lock` to return to real guidance. Unlock/lock, enable, position, scale, and opacity use **AlmightreeWaypointDB**, independently of EUI profiles and EUI Unlock Mode. Preview is session-only. Scale and opacity controls are on the EUI page. Default styling works without EUI; when EUI skinning is enabled the public API resolves `eui` or `modern`, fonts, and accent. Appearance changes do not reset position or navigation settings.

All navigation, preview, and dragging are suppressed in combat, and data is refreshed after combat. Slash commands other than disable are ignored in combat. The arrow also clears during loading transitions. No client combat-time coordinate behavior is claimed from this implementation.

## Coordinate and target rules

- Use `IsSuperTrackingAnything` and `GetHighestPrioritySuperTrackingType`, checked against the client's public enums. Retained quest IDs or placed pins never override the active type. Unsupported types hide the display.
- **Manual pin:** require active user-waypoint tracking and a valid `GetUserWaypoint()` map/position. Use its coordinates only if that map equals the player's current map. A placed but inactive pin is ignored.
- **Quest travel:** prefer quest-specific current-map `GetNextWaypointForMap`, then `GetNextWaypoint` on the current map, then a usable native `C_Navigation.GetNextWaypointForMap` position. Read the quest instruction independently of map availability; use native waypoint description text when quest text is absent.
- **Quest objective:** use `C_QuestLog.GetQuestsOnMap(currentMapID)` only when all three travel coordinate getters successfully report no step, and neither quest nor native travel text indicates a step. Select a matching active quest ID with a matching `mapID` and usable `x/y`. At most 512 rows are examined. This deliberately uses the verified quest POI source rather than requiring task-quest APIs or legacy global POI functions.
- A quest-specific step projected onto the current map remains usable even if the global step names another map. Otherwise a known remote step, travel instruction without coordinates, malformed coordinate result, or missing/error/restricted travel getter blocks objective fallback. Unknown routing does not authorize a direct line to the final objective.
- **Area POI:** require active `MapPin` tracking, `IsSuperTrackingMapPin`, and the `AreaPOI` subtype from `GetSuperTrackedMapPin`. Prefer a current-map native travel position; otherwise query `GetAreaPOIInfo(currentMapID, areaPoiID)` only if no native step/instruction is exposed. Do not substitute `linkedUiMapID` for the coordinate map. Quest offers, taxi nodes, dig sites, housing, and other unsupported tracked types hide.
- Never subtract positions on different maps or guess map translations. The first prototype does not project manual pins between maps or implement routes, floor conversion, transports, or pathfinding. It hides the arrow when coordinates, map dimensions, or facing cannot be validated. A known target and useful instruction can remain visible with “Direction unavailable.”

Map coordinates must be finite nonrestricted normalized numbers in `[0,1]`, map IDs positive integers, and `GetMapWorldSize` width/height finite positive values. For a shared map: east = `(targetX-playerX)*width`, north = `(playerY-targetY)*height`. Bearing is `atan2(-east,north)` and texture rotation is bearing minus `GetPlayerFacing()`, wrapped to `[-pi,pi)`. The north/up arrow uses the WoW facing convention (zero north, positive toward west). The implementation includes a Lua 5.1-compatible `atan2` fallback. Tests verify cardinal directions, rectangular-map scaling, facing, and wraparound; the actual client texture rotation and map/facing interpretation still require the turning test below.

The displayed **Straight-line** distance is the planar distance in yards to the selected current-map point, not route length, remaining portal distance, or proof of arrival. It is computed from the same validated coordinates as the arrow. The prototype deliberately does not display `C_Navigation.GetDistance()`: observations show that value can briefly belong to a previous target. Native distance zero, navigation state, and screen validity are not used to declare arrival. Coincident coordinates can display `~0 yd` with no directional bearing; tracking is never cleared automatically.

## Refresh and stale-data handling

Tracking/path, user-pin, quest/area-POI, zone, arrival, world-transition, and combat events clear all displayed target fields immediately. No old destination, instruction, bearing, or distance survives invalidation. New target identity is read after a short event-coalescing delay, then reread before publishing a fresh snapshot. A new identity starts another short refresh pass. The initial wait can therefore span two 0.25-second passes; this is a scheduling policy, **not a guaranteed Blizzard readiness interval**.

While a valid bearing exists, fresh snapshots run at most 10 times per second; known targets without direction retry at most twice per second. Identity is checked even if an event is missed, and rechecked after data collection. Removal, disable, combat, loading, and identity mismatch discard results. No timer callback holds an old quest ID or model, and a generation check prevents publishing work invalidated during a getter. There are no `C_Timer` callbacks to survive disable/re-enable. With no supported target, or while disabled, previewing, or unlocking, there is no active `OnUpdate` handler. Preview/mover is static.

Blizzard does not provide an atomic target-and-route snapshot/readiness token. Fresh waypoint getters can still transiently disagree with tracking while the client settles. The coalescing delay does not prove readiness; quest-specific waypoints take precedence, unknown travel blocks objective fallback, and subsequent bounded refreshes correct changing data. Capture/report any visible wrong-target step in game; do not mark this risk resolved solely from delay timing or mocked tests.

## Exact in-game validation

Run out of combat on Retail first, with script errors visible. Keep named probe batches per scenario if collecting data. Record client/build, addon revision, EUI version, location/map, target ID, expected/actual result, errors, and pass/fail/blocked. These steps are **pending**, not automated passes.

1. **Preview and position:** `/atway enable`, `/atway preview`, `/atway unlock`. Drag the panel to another location, run `/atway lock`, then `/atway preview` to exit explicit preview. `/reload` and check position persists. `/atway reset` should move only the panel; it must not change tracking. Repeat at another UI scale and using the EUI scale/opacity controls.
2. **Manual pin and inactive pins:** on the current zone map, place a pin east of the player and explicitly choose to track it using Blizzard's normal controls. With the player facing north, the arrow should point right. Turn right to face the pin; it should point up. Face away; it should point down. Rotate the camera alone while stationary: the arrow should remain relative to the player's facing. Do not use EUI `/way` to establish correctness of this test.
3. **Move:** walk toward the pin and then away. Straight-line distance should decrease and increase, and the bearing should follow lateral movement. Repeat with a north/west/south pin and on a map with unequal width/height. At the exact position, do not expect arrival clearing or an invented bearing. Untrack the pin while leaving it placed; the display must clear. Track a pin on another map: direction must hide instead of comparing unrelated coordinates.
4. **Quest POI:** after any required travel step is complete, explicitly supertrack quest `88994` on player map `2413` when the quest is available. Compare the selected POI with **54.18, 53.13** (observed normalized `.5418,.5313`). Turn and walk toward/away from that position; check direction and straight-line distance. Highlighting a different quest in the log alone must not switch guidance unless Blizzard's active tracking changes.
5. **Switching:** explicitly track quest `88996`; compare with **64.65, 38.63** (`.6465,.3863`) in the observed scenario. Switch `88994` → `88996` → manual pin → quest, including switches within 0.25 seconds. The old panel must clear on each event, then show the fresh target without restoring the previous label/distance/instruction. These coordinates are user-observed fixtures, not hardcoded data or guaranteed locations for every phase/client.
6. **Removal and stop:** clear tracking using Blizzard controls. The display must disappear and active updates stop. Change a target and immediately `/atway disable`; wait at least two seconds. It must stay hidden. Re-enable and verify only the currently tracked target appears. Repeat disable/re-enable during rapid switches and after clearing all tracking.
7. **Portal before travel:** with quest `88994` available on map `2393`, verify the arrow chooses Blizzard's supplied current-map portal step and retains **“Take the portal from Silvermoon to Harandar.”** It must not point directly to the final objective. If only text or a step on another map is available, direction must hide while useful text remains. The planar distance here is to the step, not the quest's final objective.
8. **Portal after travel:** take the portal normally. During loading, guidance must clear. On player map `2413`, when the travel getters return nil and instruction clears, verify the quest POI fallback points to `.5418,.5313`. Confirm it changes to `.6465,.3863` when switching to `88996`. Record how long native text/steps persist; do not assume 0.24/0.25 seconds is a readiness guarantee.
9. **Unavailable contexts:** test a different floor, instance, vehicle, missing player position/facing, native navigation disabled, and a remote target. Expect hiding or text-only output where shared coordinates cannot be established. Test an Area POI independently of quests; unsupported map-pin subtypes must not be treated as Area POIs. No missing routing data should create a guessed route.
10. **Combat/loading:** enter combat while tracking and while dragging/previewing. The panel should hide; disable must remain effective. After combat, reacquire current state. Cross a loading screen and zone boundary. Compare errors/taint/protected-action reports with an addon-disabled baseline; suppressing combat updates is not evidence of taint-free behavior.
11. **EUI and fallback:** `/atway options` must open a separate plugin section with working enable, preview, unlock, reset, scale, and opacity controls. Test EUI's resolved `eui` and `modern` skins, accent/font changes, and per-addon third-party skinning disabled. Settings and position should persist across looks changes. Test with EUI absent and with its `/way` module both enabled/disabled for coexistence. Confirm neither addon changes Blizzard tracking except through the player's normal controls.

## Automated checks and sources

From the repository root, run `lua tests/run.lua` with a Lua interpreter, or `fengari tests/run.lua` with Fengari. The current run passed under **Fengari / Lua 5.3 semantics**. WoW embeds a different runtime and UI; these checks do not execute inside it.

- `Navigation.test.lua`: cardinal/aspect-ratio math, player-facing subtraction, finite/restricted input validation, map mismatch, coincident points, active-type precedence, pins, quest travel/objective selection, observed coordinate fixtures, remote/unknown travel blocking, missing/error/restricted APIs, instructions without a usable map, Area POIs, switching/removal, generation invalidation, combat/loading suppression, stop/idle/preview behavior, and never reading native distance.
- `Display.test.lua`: owned-frame contracts, text escaping/clearing, rotation visibility, fallback/public-skin hooks, settings widgets without prebuild side effects, dragging/reset, entrypoint loading without EUI, and idle shutdown. Mocks do **not** verify actual texture rendering, EUI internals, style pixels, font metrics, or client drag/UI-scale behavior.
- `WaypointProbe.test.lua`: the preserved probe regression suite, including settled capture cancellation and bounded sampling.
